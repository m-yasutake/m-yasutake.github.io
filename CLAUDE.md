# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`tomika.bike` — a static site (deployed via GitHub Pages, custom domain in `CNAME`) documenting a cycling trip through Japan, Denmark, and Norway. No build step, no bundler, no framework: plain HTML/CSS/vanilla JS pages, backed by Firebase (Firestore + Storage) for dynamic data and a set of Node scripts/GitHub Actions that keep static JSON/PMTiles snapshots in the repo fresh.

## Running locally

There's no dev server dependency in the root — just serve the static files:

```
npx serve . -p 8080
```

(This is also wired up as the VS Code task "Start Local Server" in `.vscode/tasks.json`.) Open `index.html` etc. directly against `http://localhost:8080`.

## Repo layout

Config files live in `config/`: `firebase.json`, `firestore.rules`, `storage.rules`, `cors.json`, `eslint.config.js`. `firebase.json`'s rule paths are relative to its own location, so **any `firebase` CLI command must pass `--config config/firebase.json`** (e.g. `firebase deploy --only firestore:rules,storage:rules --config config/firebase.json`) — without it the CLI falls back to looking for `firebase.json` at the repo root and won't find it. `package.json`'s `lint` script already passes the flag for ESLint, so `npm run lint` needs no extra flags.

A handful of files can't move even though they'd otherwise belong in `config/` or similar: `CNAME` must stay at the repo root for GitHub Pages' custom-domain lookup, and `package.json`/`package-lock.json` must stay at the root for `npm`/`eslint` to auto-discover without extra flags. HTML pages, and everything under `js/`, `css/`, and `assets/` that's referenced by a `<script src>`/`<link href>`, also stay put — their paths are effectively public URLs (this is a static site with no build step or router), so moving them silently breaks bookmarks/links/CI. `admin.html`'s per-section JS lives in `js/admin/` (one file per dashboard section — photos, videos, blog, gear, map data, etc.).

## The `scripts/` Node project

`scripts/` is a separate Node package (own `package.json`, Node >= 20) used only by GitHub Actions / manual data refreshes — it is not part of the deployed site.

```
cd scripts
npm install
npm run tiles    # node generate-pmtiles.js        - rebuild assets/tiles/*.pmtiles from Firebase GPX
npm run points   # node generate-points-snapshot.js - export Firestore points -> assets/*points.json
npm run strava   # node fetch-strava-rides.js       - pull new Strava rides into Firebase + assets/stats.json
```

`fetch-norway-facilities.js` (Overpass API -> `assets/norway-facilities.json`) is run directly with `node` and needs no credentials.

All of these require a `FIREBASE_SERVICE_ACCOUNT` env var (JSON service-account key for the `roots-eddf5` Firebase project) except the Overpass one. `fetch-strava-rides.js` additionally needs `STRAVA_CLIENT_ID` / `STRAVA_CLIENT_SECRET` / `STRAVA_REFRESH_TOKEN`. See the header comments in each script and in `.github/workflows/*.yml` for the full env var list (trip date ranges, optional overrides, etc).

`npm run lint` (root `package.json`) runs ESLint over `js/` and `scripts/` using `config/eslint.config.js` — see that file's comments for why `no-undef` is off for `js/`. There is no test tooling configured anywhere in this repo — don't invent commands for it.

## Architecture

### Static pages + generated data snapshots

The site avoids client-side Firestore queries wherever possible by baking data into static JSON checked into `assets/` and regenerated by scheduled/dispatched GitHub Actions (`.github/workflows/`):

- `assets/stats.json` — trip stats (distance/elevation/days), updated nightly by `fetch-strava-rides.yml`.
- `assets/points.json`, `assets/norway-points.json`, `assets/denmark-points.json` — exported Firestore map points, regenerated by `generate-points-snapshot.yml` (manual or via `repository_dispatch` type `regenerate-points`).
- `assets/norway-facilities.json` — OSM/Overpass facility data (water, toilets, shelters), refreshed weekly.
- `assets/tiles/*.pmtiles` + `assets/tiles/my-routes-manifest.json` — vector tiles for ridden routes, built by `generate-pmtiles.js` from GPX files in Firebase Storage, split into per-trip shards (japan/norway/denmark/other-`<year>`) to stay under GitHub's 100 MB file limit. Regenerated by `generate-tiles.yml` (manual or `repository_dispatch` type `regenerate-tiles`) and automatically as a follow-up job in `fetch-strava-rides.yml` when new rides are found. Each shard is only rebuilt/re-committed if its underlying GPX file set actually changed (tracked in `assets/tiles/category-fingerprints.json`) — otherwise one new ride would force fresh multi-megabyte commits for every shard, not just the one it belongs to, since PMTiles is a compressed binary format git can't usefully delta.

When editing anything that touches ride/point/tile data, know that the "source of truth" is Firebase (Firestore `routes`/`points` collections + Storage GPX files); the JSON/pmtiles files in `assets/` are just cached exports the frontend reads at load time. Don't hand-edit those generated JSON files — regenerate them via the scripts, or expect them to be overwritten by the next scheduled run.

### Frontend structure

- `js/main.js` — shared chrome: page loader, navbar scroll state, mobile hamburger menu, toast notifications, the auth modal.
- `js/site-nav.js` / `js/site-footer.js` — the navbar+mobile-menu and footer markup, shared across every page (`<nav id="site-navbar">`/`<footer id="site-footer">` placeholders + `SiteNav.init()`/`SiteFooter.init()`). Edit these, not individual pages, to change nav/footer links.
- `js/i18n.js` — a flat key -> string dictionary (`TRANSLATIONS`) for `en`/`ja`/`no`, applied to `data-i18n`-tagged elements via a global `I18n` object. Add new UI strings here for all three languages, not inline.
- `js/route-map.js` — shared read-only Leaflet map component (`RouteMap.init(elementId, opts)`) that renders only the "my routes" PMTiles overlay; used on pages that just need to show where rides have been (e.g. home, country pages) without the full planning UI. Supports `map.setTripFilter(dateFrom, dateTo)`.
- `js/country-map.js` — the shared interactive planning-map engine (`CountryMap.init(config)`): snapshot loading with server-side clustering, PMTiles route overlays, point-type filter UI, fullscreen toggle. `js/{japan,denmark,norway}-map.js` are thin per-country config files that call it (icon set, type-normalization rules, popup fields, map center — see the header comment in `country-map.js` for the full config shape). All three read their point-type rules/icons from `js/point-types.js`, which is also required by `scripts/generate-points-snapshot.js` (Node) so the frontend and the server-side clustering can't drift out of sync on which types exist.
- `js/gpx-worker.js` — Web Worker for parsing/processing GPX off the main thread.
- `js/admin/*.js` — one file per `admin.html` dashboard section (photos, videos, blog, gear, map data, onsen picker, subscribers, dashboard counts, gear links, trip settings), loaded as separate `<script>` tags in the same order as the sidebar.
- `assets/js/firebase-config.js` — the public Firebase client config (`FIREBASE_CONFIG`) plus `window.getAdminEmails(db)`, which reads admin emails from Firestore `config/admins` (no code changes needed to add/remove admins — edit that Firestore doc). The Firebase API key here is intentionally public; access is controlled by Firestore security rules and Firebase Auth authorized domains, not by hiding the key.
- Pages load Firebase via the `firebase-*-compat.js` CDN scripts (not the modular SDK) and initialize with `firebase.initializeApp(FIREBASE_CONFIG)` guarded by `if (!firebase.apps.length)`.

### Maps

Route/tile rendering uses Leaflet + Leaflet.VectorGrid + the `pmtiles` JS library, with a custom `pmtiles://` fetch interceptor (installed once per page in `route-map.js`, and similarly in the per-country map files) that resolves `pmtiles://<instanceKey>/{z}/{x}/{y}` requests against in-memory `pmtiles.PMTiles` instances rather than hitting the network per tile.

### Trip pages

Each destination has a parallel pair of pages: `<country>.html` (public trip page/blog-style, uses `route-map.js`) and `planning-<country>.html` (interactive route-planning view, uses `country-map.js` + its per-country config). `admin.html` is the single dashboard for managing all three countries' data (points/routes upload and deletion, live under its "Map Data" section) plus blog/photos/videos/gear/subscribers. `planning.html`, `roots.html`, and `journal.html` are legacy redirect stubs to current pages — don't add real content to them. Trip date ranges (used for filtering stats and routes) are configured as GitHub Actions repository variables (`JAPAN_TRIP_FROM/TO`, etc.), not hardcoded in the scripts. Note: Japan's points snapshot (`assets/points.json`) predates the multi-country feature — Firestore points are never explicitly tagged `country: 'Japan'`, so it's built as "every point not tagged Norway or Denmark" (see the comment above `COUNTRY_SNAPSHOTS` in `scripts/generate-points-snapshot.js`).
